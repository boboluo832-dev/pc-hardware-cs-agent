Tool Use 循环机制
// Orchestrator 核心循环伪代码

while (continueLoop) {
  response = await claude.messages.create({
    model, system, messages, tools,
    cache_control: { type: "ephemeral" }  // Prompt Caching
  })

  if (response.stop_reason === "tool_use") {
    // Claude 需要调用工具
    for (block of toolUseBlocks) {
      result = await executeTool(block.name, block.input)
      toolResults.push({ tool_use_id, content: result })
    }
    messages.push({ role:"assistant", content: response.content })
    messages.push({ role:"user", content: toolResults })
    // 继续循环，让 Claude 处理工具结果

  } else {  // stop_reason === "end_turn"
    // Claude 生成了最终回复，退出循环
    callbacks.onText(finalText)
    continueLoop = false
  }
}

6 核心技术亮点

1. Agent Orchestrator — Tool Use 循环引擎

实现完整的 Claude Tool Use 协议循环，模型可在单次对话中连续调用多个工具（如先查产品参数，再做兼容性检查），直到生成最终文本回复。通过 stop_reason 判断是否继续循环，确保工具调用的完整性和可控性。

关键文件：packages/server/src/agent/orchestrator.ts

2. 插件式工具注册中心 (Tool Registry)

基于 Map + ToolDefinition 接口的动态注册机制。新增工具只需实现接口并调用 registerTool()，零侵入核心代码。支持工具的运行时启用/禁用（灰度上线能力），统一的错误捕获和结果序列化。

关键文件：packages/server/src/tools/registry.ts

3. 硬件兼容性规则引擎

覆盖 6 种兼容性检查类型，基于产品 specs JSON 的动态规则匹配（非硬编码）。不兼容时自动提供替代方案建议。策略模式实现，通过 check_type 映射到对应的检查函数。

关键文件：packages/server/src/tools/compatibility-check.ts

4. WebSocket 流式响应管道

端到端流式架构：Orchestrator 通过 StreamCallbacks 接口实时推送文本片段 → WebSocket frame 传输 → 前端 useChat Hook 维护流式缓冲区逐步拼接渲染。用户感知延迟从"等待完整回复"降低到"首个 token 到达即开始显示"。

关键文件：packages/server/src/api/routes.ts + packages/widget/src/hooks/useChat.ts

5. Web Component 嵌入式架构

Custom Element + Shadow DOM 实现完全样式隔离，不受宿主页面 CSS 影响。Vite Library Mode 打包为 IIFE 单文件，支持 CDN 分发。宿主页面只需 <cs-agent-widget data-ws-url="..."> 一行标签即可嵌入。

关键文件：packages/widget/src/embed.ts

6. 动态 System Prompt + Slot Filling

System Prompt 根据会话进展动态注入已收集的上下文（产品型号、购买日期、问题分类）。Slot Filling 模式逐步收集用户信息，让 AI 在后续回复中更精准地解决问题，避免重复询问。

关键文件：packages/server/src/prompts/system.ts + packages/server/src/session/store.ts

7. Monorepo 工程化

pnpm Workspaces 管理 3 个包（shared/server/widget），Turborepo 实现依赖感知的并行构建。共享类型定义包 @cs-agent/shared 确保前后端接口契约一致，编译期即可发现类型不匹配。

关键文件：pnpm-workspace.yaml + turbo.json + packages/shared/src/index.ts

Q 面试题 — 架构设计类

为什么选择 Monorepo 而不是多仓库？这个项目规模有必要吗？ 架构 ▼

核心理由：类型安全的跨包共享。

这个项目有 3 个包：shared（类型定义）、server（后端）、widget（前端）。前后端通过 WebSocket 通信，消息格式必须一致。Monorepo 让 @cs-agent/shared 的类型变更能在编译期同时被 server 和 widget 感知，避免运行时类型不匹配。

即使项目规模不大，Monorepo 的收益也很明确：

1. 一次 pnpm dev 启动所有包的开发模式
2. 类型变更即时传播，无需发包
3. Turborepo 缓存构建产物，CI 只重建变更的包

面试加分点：如果是多仓库，shared 包每次改动都要发 npm 包 → server/widget 更新依赖 → 联调周期变长。对于紧耦合的前后端项目，Monorepo 是更务实的选择。

Tool Registry 的设计有什么优势？如果要新增一个"订单查询"工具，需要改哪些代码？ 架构 ▼

设计优势：开闭原则（OCP）的实践。

Tool Registry 基于 Map<string, ToolDefinition> + 接口抽象，核心代码（orchestrator、routes）完全不感知具体工具的存在。新增工具的步骤：

1. 创建 tools/order-query.ts，实现 ToolDefinition 接口（name、description、input_schema、handler）
2. 在 tools/index.ts 中调用 registerTool(orderQueryTool)
3. 完成。Orchestrator 自动通过 getEnabledTools() 获取新工具定义传给 Claude

零侵入核心代码：不需要修改 orchestrator.ts、routes.ts 或任何已有工具文件。

额外能力：enabled 字段支持灰度上线——可以先注册但不启用，通过配置或 Admin API 动态开关。

流式响应的端到端设计是怎样的？如果网络中断怎么处理？ 架构 ▼

三层流式管道：

1. Orchestrator 层：通过 StreamCallbacks.onText(chunk) 接口，每收到 Claude 的文本片段就触发回调
2. 传输层：WebSocket route 在 onText 回调中立即 socket.send({ type:"stream", content })
3. 渲染层：useChat Hook 维护 streamBufferRef，每收到 stream 事件就拼接并触发 React 状态更新

网络中断处理：

• 前端 ws.onclose 触发 3 秒后自动重连
• 重连后通过 sessionId 恢复已有会话（历史消息保留在服务端 Session 中）
• 当前正在生成的回复会丢失，但用户可以重新发送消息继续对话

改进方向：可以加入消息 ACK 机制和客户端消息队列，实现断线期间消息的可靠投递。

Q 面试题 — AI / LLM 类

Tool Use 循环如何防止无限调用？有没有可能 Claude 一直调用工具不停？ AI ▼

Claude API 自身有终止机制：

每次 API 调用返回的 stop_reason 只有两种值："tool_use"（需要调用工具）或 "end_turn"（生成最终回复）。Claude 在获得足够信息后会自然地选择 end_turn。

额外的安全措施（可以在面试中提到的改进方向）：

1. 设置最大循环次数（如 max_iterations = 10），超过则强制退出并返回已有文本
2. 设置单次对话的 token 预算上限
3. 在 System Prompt 中明确指导："如果工具未返回有用结果，不要重复调用，直接告知用户"

实际经验：在 PC 硬件客服场景中，典型对话只需 1-2 次工具调用（查参数 + 检兼容性），极少超过 3 次。

System Prompt 为什么要动态注入会话上下文？直接让 Claude 从历史消息中提取不行吗？ AI ▼

三个原因：

1. 减少 Token 消耗：历史消息可能很长，但关键上下文（产品型号、问题分类）只需几行。动态注入到 System Prompt 中，Claude 不需要每次都从长历史中"重新理解"

2. 提升准确性：结构化的上下文（"用户咨询的产品型号：CASE-ATX-001"）比让模型从自然语言对话中提取更可靠，避免遗漏或误解

3. 配合 Prompt Caching：System Prompt 的静态部分（角色定义、行为准则）可以被缓存，只有动态上下文部分变化。使用 cache_control: ephemeral 可以让 Anthropic 缓存不变的前缀，降低重复调用成本

Slot Filling 模式：随着对话进展，逐步收集 productModel、purchaseDate、issueCategory 等信息填入上下文，让后续回复越来越精准。

为什么用关键词匹配做知识库搜索，而不是向量数据库 + Embedding？ AI ▼

务实的技术选型，匹配当前场景：

1. 数据规模小：知识库只有 7 篇结构化文档，向量检索的优势在大规模非结构化文本中才体现

2. 内容高度结构化：每篇文档有明确的 category（troubleshooting/faq/policy）和 product_line（case/psu/cooler），分类过滤 + 关键词匹配已经足够精准

3. 部署简单：SQLite 零依赖，不需要额外的 Embedding 模型服务或向量数据库（Pinecone/Milvus）

4. 成本低：不需要为每次查询调用 Embedding API

什么时候该切换到向量数据库：

• 知识库超过 100 篇文档
• 用户查询方式多样化（同义词、口语化表达多）
• 需要语义理解而非关键词匹配

面试加分：展示了"不过度工程化"的判断力——选择匹配当前规模的方案，同时清楚演进路径。

Prompt Caching 是怎么工作的？在这个项目中节省了多少成本？ AI ▼

Anthropic Prompt Caching 原理：

通过在 messages.create 请求中标记 cache_control: { type: "ephemeral" }，Anthropic 会缓存 System Prompt 的前缀部分。同一会话的后续请求如果前缀相同，就不需要重新处理这部分 token。

在本项目中的应用：

• System Prompt 约 800 tokens（角色定义 + 行为准则 + 产品线知识 + 处理策略）
• 每次 Tool Use 循环都会重新调用 API，但 System Prompt 的静态部分不变
• 一次典型对话（2-3 轮工具调用）可以节省约 1600-2400 tokens 的输入处理成本

缓存命中条件：请求的前缀（system + 前面的 messages）与缓存完全匹配。动态上下文放在 System Prompt 末尾，最大化可缓存的前缀长度。

Q 面试题 — 前端工程类

为什么用 Web Component 而不是 iframe 来实现可嵌入式 Widget？ 前端 ▼

Web Component + Shadow DOM vs iframe 对比：

性能：iframe 创建独立的浏览上下文（独立的 DOM 树、CSS 引擎、JS 引擎），内存开销大。Web Component 共享主页面的 JS 运行时，只隔离 CSS。

通信：iframe 跨域通信需要 postMessage，异步且繁琐。Web Component 直接通过 DOM 属性（data-*）和事件通信，同步且简单。

样式隔离：Shadow DOM 提供等价于 iframe 的 CSS 隔离效果——宿主页面的样式不会泄漏进来，Widget 的样式也不会影响宿主。

SEO 和可访问性：Web Component 的内容对搜索引擎和屏幕阅读器可见，iframe 内容默认不可索引。

体积：不需要加载完整的 HTML 文档，Widget 打包为 ~30KB 的 IIFE 单文件。

唯一 iframe 更好的场景：需要完全的 JS 沙箱隔离（防止恶意代码访问宿主页面）。客服 Widget 是自有代码，不需要这种级别的安全隔离。

为什么选 Preact 而不是 React？Widget 场景有什么特殊考虑？ 前端 ▼

核心原因：体积。

• React + ReactDOM：~40KB gzipped
• Preact：~3KB gzipped

Widget 是嵌入到别人的网站中的第三方脚本，体积直接影响宿主页面的加载性能。13 倍的体积差距在 Widget 场景中是决定性因素。

为什么 Preact 够用：

• Widget 的 UI 复杂度低（聊天窗口 + 消息列表 + 输入框），不需要 React 的 Concurrent Mode、Suspense 等高级特性
• Preact 的 Hooks API 与 React 完全兼容（useState、useEffect、useRef、useCallback 都有）
• Vite 对 Preact 的支持完善，开发体验无差异

IIFE 打包的考虑：Widget 不能假设宿主页面用什么框架，所以打包为自包含的 IIFE，不依赖全局的 React 实例。Preact 的小体积让这个方案可行。

useChat Hook 的流式渲染是怎么实现的？为什么用 Ref 而不是 State 做缓冲区？ 前端 ▼

流式渲染机制：

1. WebSocket 收到 type:"stream" 事件，将 content 追加到 streamBufferRef.current
2. 调用 setMessages() 更新最后一条 assistant 消息的 content 为缓冲区全文
3. 收到 type:"done" 时，用最终消息替换临时的 streaming 消息，清空缓冲区

为什么用 Ref 做缓冲区：

• 避免闭包陷阱：WebSocket 的 onmessage 回调在 useEffect 中注册，如果用 useState 存缓冲区，回调中拿到的永远是注册时的旧值（闭包捕获）
• 避免不必要的重渲染：Ref 的变更不触发组件重渲染，只有最终调用 setMessages 时才触发一次渲染
• 高频更新场景：流式响应可能每 50ms 就有一个 chunk，如果每次都 setState 会导致过多的重渲染。用 Ref 累积，再批量更新 State

注意：实际代码中每个 stream chunk 都会 setMessages（为了实时显示打字效果），但缓冲区本身用 Ref 避免了闭包问题。如果性能敏感，可以加 requestAnimationFrame 节流。

Q 面试题 — 后端工程类

Session 为什么用内存 Map 而不是 Redis？什么时候需要切换？ 后端 ▼

当前选择的合理性：

• 单实例部署，不需要跨进程共享会话
• 会话 TTL 30 分钟，数据量可控（客服对话通常 5-10 分钟结束）
• 内存 Map 读写 O(1)，零网络延迟，零运维成本
• 会话数据不需要持久化（客服对话结束即可丢弃）

需要切换到 Redis 的信号：

1. 多实例部署：负载均衡后用户可能被路由到不同实例，需要共享会话
2. 内存压力：并发会话数超过数千，每个会话的消息历史占用显著内存
3. 服务重启恢复：需要在部署/重启后恢复活跃会话
4. 会话分析：需要持久化对话记录用于质量分析

代码已预留切换路径：Session Store 模块封装了 createSession/getSession/updateSessionContext 接口，切换存储后端只需修改这一个文件的内部实现。

为什么提供 HTTP 和 WebSocket 两种通信方式？各自适用什么场景？ 后端 ▼

双通道设计的考虑：

WebSocket (/ws) — 前端 Widget 使用：

• 支持流式推送，用户看到"打字机效果"，体验好
• 长连接复用，多轮对话无需重复建连
• 双向通信，服务端可主动推送（如超时提醒）

HTTP POST (/api/chat) — 简单集成使用：

• 无状态，适合服务端到服务端调用（如其他系统集成）
• 不需要维护长连接，适合低频调用
• 更容易做负载均衡和 API 网关代理
• 适合不支持 WebSocket 的环境（某些企业防火墙）

实现差异：HTTP 模式等待完整回复后一次性返回（onDone 才 resolve），WebSocket 模式逐片段推送（每个 onText 都 send）。

Fastify 相比 Express 有什么优势？为什么选它？ 后端 ▼

选择 Fastify 5 的理由：

1. 性能：基于 JSON Schema 的序列化优化，吞吐量是 Express 的 2-3 倍
2. 原生 WebSocket：通过 @fastify/websocket 插件无缝集成，路由级别的 WS 支持（不需要单独的 ws 服务器）
3. TypeScript 友好：内置完善的类型定义，泛型路由（app.post<{ Body: T }>）提供请求体类型推断
4. 插件系统：封装良好的插件注册机制，路由可以按功能模块拆分注册
5. Schema 验证：内置 JSON Schema 验证，可以在路由级别声明请求/响应格式

在本项目中的体现：WebSocket 路由和 HTTP 路由在同一个 Fastify 实例中共存，通过 app.register() 模块化注册，代码组织清晰。

Q 面试题 — 数据库类

为什么选 SQLite 而不是 PostgreSQL 或 MongoDB？WAL 模式有什么作用？ 数据库 ▼

SQLite 的适用性：

• 嵌入式：零配置、零运维，随应用启动，不需要独立的数据库服务进程
• 数据特征匹配：产品规格和知识库是结构化数据，关系型查询（JOIN、WHERE、LIKE）比文档型更自然
• 规模匹配：11 个产品 + 7 篇知识库文档，SQLite 单文件完全胜任
• 部署简单：一个 .db 文件跟随代码部署，不需要额外的数据库基础设施

WAL (Write-Ahead Logging) 模式的作用：

• 默认的 journal 模式下，写操作会阻塞所有读操作
• WAL 模式允许读写并发：多个读操作可以和一个写操作同时进行
• 在客服场景中：Admin 后台写入新产品数据时，不会阻塞正在进行的客服对话查询
• 代码中通过 db.pragma("journal_mode = WAL") 一行启用

什么时候该换 PostgreSQL：多实例部署、需要全文搜索（pg_trgm）、数据量超过 GB 级、需要复杂事务。

产品规格（specs）为什么存为 JSON 字符串而不是拆成多列？ 数据库 ▼

核心原因：不同品类的规格字段完全不同。

• 机箱：max_gpu_length、max_cooler_height、supported_motherboards、fan_slots
• 电源：wattage、connectors、modular_type、efficiency_rating
• 散热器：supported_sockets、tdp、fan_size、noise_level

如果拆成列，要么建 4 张不同的表（过度规范化），要么一张宽表有大量 NULL 列（稀疏矩阵）。

JSON 存储的优势：

• 灵活的 Schema：新增产品线不需要 ALTER TABLE
• 工具层直接 JSON.parse(specs) 获取结构化对象，按需取字段
• Admin 后台可以直接编辑 JSON，所见即所得

权衡：牺牲了 SQL 层面对 specs 内字段的直接查询能力。但在本项目中，查询入口是 SKU/名称，specs 只在查到产品后由应用层解析使用，所以这个权衡是合理的。

如果用 PostgreSQL：可以用 JSONB 类型 + GIN 索引，既保留灵活性又支持 JSON 路径查询。

知识库搜索的关键词匹配有什么局限性？如何改进？ 数据库 ▼

当前实现：将查询文本按空格拆分为关键词，每个关键词对 title 和 content 做 LIKE '%keyword%' 模糊匹配。

局限性：

1. 无语义理解："电脑不开机" 搜不到 "电源无法启动" 的文档
2. 无相关性排序：返回结果没有按匹配度排序，LIMIT 5 可能漏掉最相关的
3. 性能：LIKE '%x%' 无法使用索引，全表扫描（当前数据量小所以不是问题）
4. 中文分词：按空格拆分对中文不友好，"散热器不转" 会被当作一个整体

渐进式改进方案：

• 短期：SQLite FTS5 全文搜索扩展 + jieba 分词，支持中文分词和 BM25 排序
• 中期：加入同义词表（"不开机" = "无法启动" = "没反应"），扩展查询
• 长期：向量数据库 + Embedding，实现真正的语义搜索

但在当前场景中：Claude 本身会根据用户描述选择合适的搜索关键词传给工具（通过 Prompt 指导），所以 LLM 充当了"语义理解层"，弥补了关键词匹配的不足。

Q 面试题 — 工程化类

Turborepo 在这个项目中解决了什么问题？没有它会怎样？ 工程化 ▼

Turborepo 解决的核心问题：构建编排。

3 个包之间有依赖关系：server 和 widget 都依赖 shared。构建顺序必须是 shared → server/widget（并行）。

没有 Turborepo 的痛点：

• 手动维护构建顺序（写 shell 脚本串联 build 命令）
• 改了 shared 的类型后，要手动重新构建 server 和 widget
• CI 中每次都全量构建所有包，即使只改了 widget 的样式

Turborepo 提供的能力：

1. 依赖感知：自动分析包间依赖，确定正确的构建顺序
2. 并行执行：无依赖关系的任务自动并行（server 和 widget 同时构建）
3. 增量构建：基于文件 hash 的缓存，未变更的包跳过构建
4. 任务管道：turbo.json 中声明 build/dev/test 的依赖关系

实际效果：pnpm dev 一条命令同时启动 server（tsx watch）和 widget（vite dev），shared 变更时自动触发下游重编译。

Widget 为什么打包为 IIFE 而不是 ESM？有什么权衡？ 工程化 ▼

IIFE (Immediately Invoked Function Expression) 的必要性：

Widget 是嵌入到第三方网站的脚本，无法假设宿主页面的构建环境：

• 宿主可能是纯 HTML 页面（无构建工具），只能用 <script src="..."> 加载
• 宿主可能用 Webpack/Vite/Rollup 等不同打包器，ESM 的 import map 配置各异
• 宿主可能不支持 ES Modules（老旧浏览器或特殊环境）

IIFE 的优势：

• 自执行、自包含，加载即运行，零配置
• 不污染全局作用域（所有代码在闭包内）
• 兼容所有加载方式：<script>、动态 createElement('script')、CDN

权衡：不支持 Tree Shaking（但 Widget 本身就是最终产物，不需要被其他代码 import）。不支持代码分割（但 Widget 体积小，单文件加载更快）。

Vite Library Mode 配置：build.lib.formats: ['iife'] + build.lib.name: 'CSAgentWidget'，输出 cs-agent-widget.iife.js 单文件。
