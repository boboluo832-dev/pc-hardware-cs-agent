1 项目概述类

请介绍一下你的这个项目，它解决了什么问题？ 项目▼

这是一个面向 PC 硬件公司的 AI 智能客服系统。公司产品线包括机箱、电源、散热器和带屏幕的智能产品。

解决的核心问题：

  • 售前：用户经常问"我的机箱能不能装某张显卡/某个散热器"，传统客服需要查表对比参数，AI Agent 可以自动调用兼容性检测工具给出结论
  • 售后：屏幕不亮、电源异响等故障排查有标准流程，AI 可以从知识库中检索并引导用户逐步排查
  • 效率：7×24 小时自动应答，减少人工客服重复劳动，复杂问题再转人工

技术上的核心是基于 Claude 的 Tool Use（Function Calling）能力，让 AI 不只是聊天，而是能主动调用工具查数据库、做计算，然后基于工具返回的结果生成准确回复。

用具体数据说明规模：覆盖 4 条产品线、11 个 SKU、6 种兼容性检查类型、7 篇知识库文档。展示你对项目边界的清晰认知。
为什么选择自己做这个项目？动机是什么？ 动机▼

技术动机：

  • 想深入实践 LLM 应用开发中最核心的模式——Tool Use / Function Calling，不只是调 API 生成文本，而是让 AI 具备"行动能力"
  • 想验证一个完整的 AI Agent 从前端到后端到数据层的全链路实现
  • 想探索 AI 辅助开发（Claude Code）在实际项目中的效率提升

业务动机：

  • PC 硬件兼容性是一个非常适合 Tool Use 的场景——需要查数据、做比较、给结论，不是纯文本生成
  • 客服场景有明确的输入输出、可量化的成功标准（问题是否解决），适合作为 AI Agent 的落地场景
强调"选择这个场景是因为它天然适合 Tool Use"——展示你对 AI 能力边界的理解，知道什么场景适合用 AI、什么不适合。
这个项目的整体数据流是怎样的？从用户输入到最终回复经历了哪些步骤？ 数据流▼

完整链路（以"我的机箱能装 RTX 4090 吗"为例）：

  • 1. 用户在 Chat Widget 输入消息 → useChat Hook 通过 WebSocket 发送 JSON
  • 2. Fastify Server /ws 路由接收 → 恢复/创建 Session
  • 3. Orchestrator 构建请求：System Prompt + 历史消息 + 3 个工具定义
  • 4. 调用 Claude Messages API → Claude 返回 stop_reason: "tool_use"
  • 5. 解析 tool_use block → Tool Registry 执行 check_compatibility
  • 6. 工具查询 SQLite → 比较 max_gpu_length vs 用户显卡长度 → 返回兼容性结论
  • 7. 将 tool_result 回传 Claude → Claude 生成自然语言回复
  • 8. 通过 WebSocket stream 事件逐片段推送到前端
  • 9. useChat Hook 拼接流式片段，实时渲染"打字机效果"

关键点：步骤 4-7 可能循环多次（如先查产品参数，再做兼容性检查），直到 Claude 返回 stop_reason: "end_turn" 才退出循环。

2 技术栈选型类

这个项目用到了哪些核心技术？为什么选择这些技术？ 技术栈▼

核心技术栈：

  • TypeScript — 全栈语言，前后端共享类型定义，编译期发现接口不匹配
  • Claude API (Anthropic SDK) — LLM 引擎，选择 Claude 是因为其 Tool Use 能力成熟、响应质量高
  • Tool Use / Function Calling — 让 AI 不只生成文本，还能调用工具执行操作
  • Prompt Engineering — 动态 System Prompt + Slot Filling + Prompt Caching
  • WebSocket — 实时流式推送 AI 回复，用户体验远优于 HTTP 轮询
  • Fastify 5 — 高性能 Node.js 框架，原生 WebSocket 支持
  • SQLite (WAL mode) — 嵌入式数据库，零运维，适合结构化知识库
  • Preact + Web Component — 极小体积的可嵌入式 UI 组件
  • pnpm + Turborepo — Monorepo 工程化，并行构建
不要只列技术名，要说"为什么选它而不是替代方案"。比如选 Fastify 而不是 Express 是因为性能和原生 WS 支持；选 SQLite 而不是向量数据库是因为数据结构化且规模小。
为什么选 Claude 而不是 GPT-4 或其他 LLM？ 选型▼

选择 Claude 的理由：

  • Tool Use 能力成熟：Claude 的 Function Calling 实现稳定，stop_reason 机制清晰（tool_use / end_turn），循环控制可靠
  • 中文能力强：客服场景全中文交互，Claude 的中文理解和生成质量优秀
  • Prompt Caching：Anthropic 提供 cache_control 机制，可以缓存 System Prompt 的静态部分，降低多轮对话的 Token 成本
  • 安全性：Claude 的 Constitutional AI 训练使其在客服场景中更不容易产生不当回复

与 GPT-4 的对比：

  • GPT-4 的 Function Calling 也很成熟，但 Prompt Caching 机制不同（OpenAI 是自动缓存，Anthropic 是显式标记）
  • Claude 的上下文窗口更大（200K），适合长对话历史
  • 实际选择也考虑了 API 可用性和成本
展示你对多个 LLM 平台的了解，而不是"只会用一个"。提到你评估过替代方案，最终基于具体需求做出选择。
为什么选 TypeScript 而不是 Python？AI 项目不是 Python 更常见吗？ 选型▼

选 TypeScript 的理由：

  • 全栈统一：前端 Widget（Preact）和后端（Fastify）用同一语言，共享类型定义包，接口契约编译期校验
  • 这不是 ML 训练项目：不需要 PyTorch/TensorFlow，只是调用 Claude API。Anthropic 的 TypeScript SDK 和 Python SDK 功能完全一致
  • WebSocket 生态：Node.js 的异步 I/O 模型天然适合 WebSocket 长连接场景
  • 部署简单：单一运行时（Node.js），不需要 Python 虚拟环境管理

如果项目涉及模型微调、Embedding 计算、向量检索等 ML 密集操作，Python 会是更好的选择。但纯 API 调用 + Web 服务的场景，TypeScript 全栈更高效。

为什么用 SQLite 而不是 PostgreSQL 或向量数据库？ 选型▼

选 SQLite 的理由：

  • 数据特征：产品规格和知识库是结构化数据（有明确的 category、product_line 字段），关系型查询比向量检索更自然
  • 规模匹配：11 个产品 + 7 篇知识库文档，向量数据库的优势在大规模非结构化文本中才体现
  • 零运维：嵌入式数据库，随应用启动，不需要独立的数据库服务
  • WAL 模式：支持读写并发——Admin 写入新数据时不阻塞客服查询

什么时候该切换：

  • 知识库超过 100 篇 → 考虑 FTS5 全文索引或向量数据库
  • 多实例部署 → 切换 PostgreSQL
  • 需要语义搜索 → 加入 Embedding + 向量检索层
展示"不过度工程化"的判断力——选择匹配当前规模的方案，同时清楚演进路径。面试官喜欢听到"我知道什么时候该升级"。

3 Claude API & Tool Use 类

什么是 Tool Use / Function Calling？它和普通的 LLM 对话有什么区别？ 核心概念▼

普通对话：用户输入 → LLM 生成文本回复。模型只能基于训练数据回答，无法获取实时信息。

Tool Use：用户输入 → LLM 判断需要调用哪个工具 → 返回工具调用请求（名称 + 参数）→ 应用层执行工具 → 将结果回传 LLM → LLM 基于工具结果生成最终回复。

关键区别：

  • LLM 不直接执行工具，只是"决定"调用什么工具、传什么参数
  • 实际执行在应用层（我的 Tool Registry），LLM 看到的是执行结果的文本
  • 这让 AI 能访问实时数据（数据库查询）、执行计算（兼容性比较）、触发操作（发邮件、创建工单）

在我的项目中：Claude 可以调用 3 个工具——查产品参数、检查兼容性、搜索知识库。它根据用户问题自主决定调用哪个。

你的 Agent Orchestrator 循环引擎是怎么实现的？为什么需要"循环"？ 核心实现▼

为什么需要循环：Claude 在一次对话中可能需要调用多个工具。比如用户问"幻影X1能装什么散热器"，Claude 可能先调用 lookup_product 查机箱的 max_cooler_height，再调用 search_knowledge_base 搜索散热器推荐。每次工具调用都需要一个完整的 API 请求-响应周期。

实现逻辑：

while (continueLoop) {
  response = await claude.messages.create({
    model, system, messages, tools
  })

  if (response.stop_reason === "tool_use") {
    // Claude 需要调用工具
    for (block of toolUseBlocks) {
      result = await executeTool(block.name, block.input)
      toolResults.push({ tool_use_id, content: result })
    }
    // 将 assistant 响应 + tool_result 加入消息历史
    messages.push({ role: "assistant", content: response.content })
    messages.push({ role: "user", content: toolResults })
    // 继续循环

  } else { // stop_reason === "end_turn"
    // Claude 生成了最终回复，退出循环
    continueLoop = false
  }
}

关键设计点：

  • stop_reason 是循环控制的唯一依据——"tool_use" 继续，"end_turn" 退出
  • tool_result 必须以 role: "user" 回传（Claude API 协议要求）
  • 每次循环都带上完整的消息历史，Claude 能看到之前所有工具的调用和结果
能画出这个循环的流程图，或者在白板上写出伪代码，说明你真正理解了 Tool Use 的工作机制，而不只是调了个 API。
Tool Use 循环如何防止无限调用？有没有可能 Claude 一直调工具不停？ 边界处理▼

Claude 自身的终止机制：

Claude 在获得足够信息后会自然选择 stop_reason: "end_turn"。在 System Prompt 中我明确指导了："如果工具未返回有用结果，不要重复调用，直接告知用户并建议转人工"。

可以加的额外安全措施（面试中提到改进方向）：

  • 设置 max_iterations = 10，超过强制退出并返回已有文本
  • 设置单次对话的 token 预算上限
  • 记录每次循环的工具调用，检测重复调用同一工具+相同参数的情况

实际经验：在 PC 硬件客服场景中，典型对话只需 1-2 次工具调用，极少超过 3 次。场景的确定性高，不容易出现无限循环。

工具定义（Tool Definition）是怎么传给 Claude 的？Claude 怎么知道有哪些工具可用？ API 协议▼

在调用 messages.create 时，通过 tools 参数传入工具定义数组。每个工具包含：

{
  name: "check_compatibility",
  description: "检查两个硬件之间的兼容性...",
  input_schema: {
    type: "object",
    properties: {
      product_sku: { type: "string", description: "产品SKU" },
      target_spec: { type: "string", description: "目标规格值" },
      check_type: { type: "string", enum: ["case_gpu","case_motherboard",...] }
    },
    required: ["product_sku", "target_spec", "check_type"]
  }
}

Claude 的决策过程：

  • Claude 阅读所有工具的 description 和 input_schema
  • 根据用户问题判断是否需要调用工具、调用哪个、传什么参数
  • description 的质量直接影响 Claude 的调用准确性——这也是 Prompt Engineering 的一部分

我的 Tool Registry 通过 getEnabledTools() 方法返回所有已启用工具的定义，自动过滤掉 enabled: false 的工具。

如果 Claude 调用了一个不存在的工具，或者传了错误的参数，怎么处理？ 错误处理▼

Tool Registry 的统一错误处理：

async function executeTool(name, input) {
  const tool = tools.get(name);
  if (!tool) return `错误：未找到工具 "${name}"`;
  if (!tool.enabled) return `错误：工具 "${name}" 当前未启用`;
  try {
    return await tool.handler(input);
  } catch (err) {
    return `工具执行出错：${err.message}`;
  }
}

设计思路：

  • 错误信息作为 tool_result 回传给 Claude，而不是抛异常中断对话
  • Claude 看到错误信息后，会自行决定：重试、换个工具、或直接告知用户
  • 这样即使工具出错，对话也不会中断，用户体验不受影响

实际上 Claude 很少传错参数：因为 input_schema 用 JSON Schema 严格定义了参数类型和枚举值，Claude 会遵守 schema 约束。

4 Prompt Engineering 类

你的 System Prompt 是怎么设计的？包含哪些部分？ Prompt▼

System Prompt 结构（约 800 tokens）：

  • 角色定位：定义 AI 是"专业的 PC 硬件客服助手"，明确服务的产品线
  • 行为准则：6 条规则，如"先确认型号再给方案"、"兼容性问题必须用工具验证"、"超出能力范围诚实告知"
  • 产品线概览：机箱/电源/散热器/智能产品的关键参数维度
  • 常见问题处理策略：屏幕不亮排查流程、兼容性咨询流程、售后服务流程
  • 语气要求：称呼"您"、表达同理心、结尾确认
  • 转人工条件：明确 4 种需要转人工的场景
  • 动态上下文（运行时注入）：当前会话已收集的产品型号、购买日期、问题分类
能说出 System Prompt 的具体结构和设计理由，展示你不是随便写了一段话，而是有策略地组织 Prompt 的各个部分。
什么是"动态 System Prompt"？为什么不让 Claude 自己从历史消息中提取上下文？ Prompt▼

动态 System Prompt 机制：根据会话进展，实时将已收集的上下文信息注入到 System Prompt 末尾。

// 动态注入的上下文示例
## 当前对话上下文
- 用户咨询的产品型号：CASE-ATX-001（幻影X1）
- 购买时间：2024年3月
- 问题分类：兼容性咨询
- 已收集信息：
  - 显卡型号：RTX 4090
  - 显卡长度：336mm

为什么不让 Claude 自己提取：

  • 减少 Token 消耗：历史消息可能很长，但关键上下文只需几行。结构化注入比让模型每次重新理解更高效
  • 提升准确性：结构化数据比从自然语言中提取更可靠，避免遗漏或误解
  • 配合 Prompt Caching：静态部分可被缓存，只有动态上下文变化。最大化可缓存前缀长度
什么是 Slot Filling？在你的项目中是怎么实现的？ Prompt▼

Slot Filling（槽位填充）：对话系统中逐步收集完成任务所需信息的模式。每个"槽位"代表一个必要信息。

在我的项目中：

  • Session 中维护 context: { productModel, purchaseDate, issueCategory, collectedSlots: {} }
  • 随着对话进展，逐步填充：用户说"我买的是幻影X1" → 填入 productModel
  • 已填充的槽位注入到 System Prompt，Claude 在后续回复中不会重复询问已知信息
  • 所有槽位填满后，Claude 可以直接给出解决方案，而不是继续追问

效果：多轮对话的效率显著提升。用户不需要在每条消息中重复说"我的产品是XX"，系统会记住并利用已有信息。

Slot Filling 是任务型对话系统的经典模式（源自 Rasa、Dialogflow 等框架），在 LLM 时代通过动态 Prompt 注入实现，比传统的状态机更灵活。
Prompt Caching 是怎么工作的？在你的项目中节省了多少成本？ 优化▼

Anthropic Prompt Caching 原理：

通过在请求中标记 cache_control: { type: "ephemeral" }，Anthropic 缓存 System Prompt 的前缀部分。同一会话的后续请求如果前缀相同，不需要重新处理这部分 token。

在本项目中的应用：

  • System Prompt 静态部分约 800 tokens（角色 + 行为准则 + 产品线 + 策略）
  • 动态上下文放在末尾，最大化可缓存的前缀长度
  • 每次 Tool Use 循环都会重新调用 API，但静态前缀被缓存
  • 一次典型对话（2-3 轮工具调用）节省约 1600-2400 tokens 的输入处理成本

缓存命中条件：请求的前缀（system + 前面的 messages）与缓存完全匹配。所以动态内容放末尾是关键设计。

能解释"为什么动态内容放末尾"——因为缓存是前缀匹配，前面不变的部分越长，缓存命中率越高。这展示了你对 Caching 机制的深入理解。

5 架构设计类

Tool Registry（工具注册中心）是怎么设计的？为什么要做成插件式？ 核心设计▼

设计：基于 Map<string, ToolDefinition> + 接口抽象的动态注册机制。

interface ToolDefinition {
  name: string;              // 工具名称
  description: string;       // 描述（给 Claude 看）
  input_schema: object;      // JSON Schema 参数定义
  handler: (input) => Promise<string>;  // 执行逻辑
  enabled: boolean;          // 是否启用
}

为什么插件式：

  • 开闭原则：新增工具不需要修改 Orchestrator、Routes 或任何已有工具的代码
  • 灰度上线：enabled 字段支持注册但不启用，可以通过配置动态开关
  • 统一错误处理：executeTool() 统一 try-catch，工具实现者不需要关心错误如何回传给 Claude
  • 可测试性：每个工具是独立函数，可以单独单元测试

新增工具的步骤：

  • 1. 创建 tools/my-tool.ts，实现 handler 函数
  • 2. 调用 registerTool({ name, description, input_schema, handler, enabled: true })
  • 3. 在 tools/index.ts 中 import。完成。
这是开闭原则（OCP）的实际应用。面试官可能追问"如果要加一个订单查询工具需要改哪些文件"——答案是"只需要新建一个文件 + 一行 import"，核心代码零修改。
硬件兼容性规则引擎是怎么实现的？为什么不硬编码规则？ 规则引擎▼

实现方式：策略模式 + 数据驱动。

6 种检查类型通过 check_type 映射到对应的检查函数：

const checks = {
  case_motherboard: () => {
    // 从 specs.supported_motherboards 数组中匹配
  },
  case_gpu: () => {
    // 比较 specs.max_gpu_length vs 用户输入的长度
  },
  case_cooler: () => {
    // 比较 specs.max_cooler_height vs 散热器高度
  },
  case_psu: () => {
    // 从 specs.supported_psu_types 数组中匹配
  },
  cooler_socket: () => {
    // 从 specs.supported_sockets 数组中匹配
  },
  psu_connector: () => {
    // 从 specs.connectors 数组中模糊匹配
  }
}
const result = checks[check_type]();

为什么不硬编码：

  • 规则依赖产品的 specs JSON 数据，不同产品的参数不同
  • Admin 后台可以修改产品 specs，规则自动适配新数据
  • 新增产品线只需在数据库中添加数据，不需要改代码
提到"策略模式"这个设计模式名称，展示你有设计模式的知识储备。同时强调"数据驱动"——规则的具体阈值来自数据库，不是代码中的魔法数字。
会话管理是怎么设计的？Session Store 为什么用内存而不是 Redis？ 状态管理▼

Session Store 设计：

  • 使用内存 Map<string, Session> 存储活跃会话
  • 每个 Session 包含：id、消息历史、上下文（Slot Filling 数据）、最后活跃时间
  • 30 分钟 TTL 过期清理，防止内存泄漏
  • 通过 sessionId 在 WebSocket 重连后恢复会话

为什么用内存：

  • 单实例部署，不需要跨进程共享
  • 客服对话通常 5-10 分钟结束，数据量可控
  • 内存读写 O(1)，零网络延迟
  • 会话数据不需要持久化（对话结束即可丢弃）

切换 Redis 的信号：多实例部署、需要服务重启恢复、并发会话数超过数千。代码已通过模块封装预留了替换路径——只需修改 session/store.ts 的内部实现。

6 WebSocket & 实时通信类

为什么用 WebSocket 而不是 HTTP 轮询或 SSE？ 通信▼

三种方案对比：

  • HTTP 轮询：客户端定时请求，延迟高（轮询间隔）、浪费带宽（大量空响应）、不适合流式输出
  • SSE (Server-Sent Events)：服务端单向推送，适合流式输出，但只能服务端→客户端，客户端发消息还需要额外的 HTTP 请求
  • WebSocket：全双工，客户端和服务端都能随时发消息，一个连接搞定所有通信

选 WebSocket 的理由：

  • 客服对话是双向交互：用户发消息 + 服务端推流式回复，WebSocket 天然匹配
  • 多轮对话复用同一连接，无需每次建连
  • 可以实现服务端主动推送（如超时提醒、转人工通知）
  • Fastify 原生支持 WebSocket，集成成本低
同时提到项目也保留了 HTTP POST 接口（/api/chat），用于不支持 WebSocket 的环境或服务端到服务端集成。展示你考虑了多种接入场景。
流式响应是怎么实现的？从服务端到前端的完整链路是什么？ 流式▼

三层流式管道：

  • Orchestrator 层：定义 StreamCallbacks 接口（onText / onDone / onError），每收到 Claude 的文本片段就触发 onText
  • 传输层：WebSocket route 在 onText 回调中立即 socket.send({ type:"stream", content })
  • 渲染层：前端 useChat Hook 维护 streamBufferRef，每收到 stream 事件就拼接并更新 React 状态

前端流式渲染细节：

ws.onmessage = (event) => {
  const data = JSON.parse(event.data);
  if (data.type === "stream") {
    streamBufferRef.current += data.content;
    setMessages(prev => {
      // 更新最后一条 assistant 消息的 content
      const last = prev[prev.length - 1];
      if (last?.id === "streaming") {
        return [...prev.slice(0,-1), {...last, content: streamBufferRef.current}];
      }
      return [...prev, {id:"streaming", role:"assistant", content: streamBufferRef.current}];
    });
  }
  if (data.type === "done") {
    // 用最终消息替换临时的 streaming 消息
    streamBufferRef.current = "";
    setMessages(prev => [...prev.filter(m => m.id !== "streaming"), data.message]);
  }
}
WebSocket 断线了怎么办？如何保证用户体验？ 容错▼

当前实现：

  • 前端 ws.onclose 触发 3 秒后自动重连
  • 重连后通过 sessionId 恢复已有会话（历史消息保留在服务端 Session 中）
  • 正在生成的回复会丢失，但用户可以重新发送消息继续对话

用户体验保障：

  • 断线期间用户发送的消息不会丢失（前端乐观更新已显示在 UI 中）
  • 重连成功后会话上下文完整恢复（Session Store 中的 context 和 messages 都在）
  • 错误时显示友好提示："抱歉，系统出现了问题，请稍后再试或联系人工客服"

可改进方向：加入消息 ACK 机制 + 客户端消息队列，实现断线期间消息的可靠投递；指数退避重连策略（3s → 6s → 12s）避免服务端压力。

useChat Hook 为什么用 Ref 做流式缓冲区而不是 State？ 前端▼

原因：避免闭包陷阱 + 减少不必要渲染。

  • 闭包陷阱：WebSocket 的 onmessage 回调在 useEffect 中注册，如果用 useState 存缓冲区，回调中拿到的永远是注册时的旧值
  • Ref 的特性：useRef 返回的对象在组件整个生命周期中保持同一引用，.current 的修改不触发重渲染
  • 性能：流式响应可能每 50ms 一个 chunk，用 Ref 累积文本，只在需要更新 UI 时才 setState

实际代码中每个 chunk 都会 setMessages（为了实时打字效果），但缓冲区本身用 Ref 确保了闭包中始终能拿到最新值。

这是 React/Preact Hooks 的经典面试题。能结合实际场景（WebSocket + 高频更新）解释为什么用 Ref，比背概念更有说服力。

7 工程实践类

为什么用 Monorepo？这个项目规模有必要吗？ 工程化▼

核心理由：类型安全的跨包共享。

项目有 3 个包：@cs-agent/shared（类型定义）、@cs-agent/server（后端）、@cs-agent/widget（前端）。前后端通过 WebSocket 通信，消息格式必须一致。

Monorepo 的具体收益：

  • shared 包的类型变更能在编译期同时被 server 和 widget 感知，避免运行时类型不匹配
  • 一次 pnpm dev 启动所有包的开发模式
  • Turborepo 缓存构建产物，CI 只重建变更的包
  • 依赖版本统一管理，不会出现 server 和 widget 用不同版本的 shared

如果是多仓库：shared 包每次改动都要发 npm 包 → server/widget 更新依赖 → 联调周期变长。对于紧耦合的前后端项目，Monorepo 是更务实的选择。

Turborepo 在项目中解决了什么问题？ 构建▼

核心问题：构建编排。

3 个包有依赖关系：server 和 widget 都依赖 shared。构建顺序必须是 shared → server/widget（并行）。

Turborepo 提供的能力：

  • 依赖感知：自动分析包间依赖，确定正确的构建顺序
  • 并行执行：无依赖关系的任务自动并行（server 和 widget 同时构建）
  • 增量构建：基于文件 hash 的缓存，未变更的包跳过构建
  • 任务管道：turbo.json 中声明 build/dev/test 的依赖关系

没有 Turborepo：手动写 shell 脚本串联 build 命令，改了 shared 要手动重建下游，CI 每次全量构建。

Widget 为什么打包为 IIFE 而不是 ESM？Web Component 有什么优势？ 前端▼

IIFE 的必要性：

Widget 嵌入到第三方网站，无法假设宿主页面的构建环境：

  • 宿主可能是纯 HTML 页面，只能用 <script src="..."> 加载
  • 宿主可能用不同的打包器，ESM 的 import map 配置各异
  • IIFE 自执行、自包含，加载即运行，零配置

Web Component (Custom Element + Shadow DOM) 的优势：

  • 样式隔离：Shadow DOM 阻止宿主 CSS 泄漏进来，也阻止 Widget CSS 影响宿主
  • 声明式使用：<cs-agent-widget data-ws-url="..."> 一行标签嵌入
  • vs iframe：性能更好（共享 JS 运行时）、通信更简单（DOM 属性 vs postMessage）

为什么选 Preact 而不是 React：Widget 是第三方脚本，体积是关键。Preact ~3KB vs React ~40KB，13 倍差距在嵌入场景中是决定性因素。

8 AI 辅助开发类

你提到用 Claude Code 进行开发，具体是怎么用的？效率提升有多大？ AI开发▼

Claude Code 在项目中的使用方式：

  • 架构设计阶段：描述需求后让 Claude Code 生成项目骨架、目录结构、包配置
  • 功能实现阶段：逐个模块实现，每次给出明确的功能描述和接口约束，Claude Code 生成实现代码
  • 调试阶段：遇到问题时描述现象，Claude Code 分析原因并修复
  • 重构阶段：代码写完后让 Claude Code 审查并优化

  • 样板代码（类型定义、配置文件、CRUD 接口）几乎零手写
  • 复杂逻辑（Tool Use 循环、兼容性规则引擎）通过描述需求 + 迭代修改完成

关键经验：

  • AI 生成的代码需要人工审查——理解每一行代码是什么意思、为什么这样写
  • 给 AI 的指令越精确，输出质量越高。模糊的需求会得到模糊的代码
  • AI 擅长实现已知模式，但架构决策（选什么技术、怎么分层）仍需人来做
强调"我理解每一行代码"——AI 是工具不是替代。面试官关心的是你是否真正掌握了技术，而不是只会让 AI 写代码。
用 AI 辅助开发和传统开发相比，你觉得最大的区别是什么？ AI开发▼

最大区别：开发者的角色从"写代码"变成"设计 + 审查 + 验证"。

  • AI 辅助：想清楚 → 描述需求 → 审查生成的代码 → 验证功能。时间花在"确保方向正确"和"验证质量"上

如果知识库规模扩大到 1000 篇文档，你会怎么改造搜索系统？ 扩展▼

渐进式改造方案：

第一步：SQLite FTS5（100-500 篇）

  • 查询改写（query rewriting）提升召回率
  • 重排序模型（reranker）提升精度

如果要支持多语言（英文、日文客服），需要改哪些地方？ 扩展▼

需要改动的层：

  • System Prompt：根据用户语言切换 Prompt 语言，或在 Prompt 中指示"用用户的语言回复"
  • 知识库：每篇文档增加 language 字段，搜索时按语言过滤
  • 产品数据：产品名称和描述做多语言版本（specs 中的数值不需要翻译）
  • Widget UI：快捷回复按钮、placeholder 文本做 i18n
  • 错误提示：工具返回的错误信息做多语言

不需要改的：

  • Orchestrator 循环逻辑——语言无关
  • Tool Registry 架构——工具的 handler 逻辑不涉及语言
  • WebSocket 通信协议——传输的是文本，语言透明

Claude 的优势：Claude 本身支持多语言，只需在 System Prompt 中指示语言策略，不需要额外的翻译服务。

这个项目最大的技术挑战是什么？你是怎么解决的？ 反思▼

最大挑战：Tool Use 循环的正确性和可靠性。

具体难点：

  • Claude API 的消息格式要求严格——tool_result 必须以 role:"user" 回传，tool_use_id 必须匹配
  • 多工具调用时的消息历史管理——assistant 的响应可能同时包含 text 和 tool_use blocks
  • 流式输出和工具调用的交织——Claude 可能先输出一段文本，再调用工具，再输出文本

解决方法：

  • 仔细阅读 Anthropic 官方文档的 Tool Use 协议规范
  • 用最简单的单工具场景先跑通，再逐步增加复杂度
  • 在 Orchestrator 中加入详细的日志，追踪每次循环的 stop_reason 和消息内容
  • 编写针对不同场景的测试用例（单工具、多工具、工具出错、无需工具）
面试官喜欢听到"具体的困难 + 具体的解决过程"，而不是泛泛而谈。提到"先跑通最简单的场景再逐步增加复杂度"展示了工程思维。
